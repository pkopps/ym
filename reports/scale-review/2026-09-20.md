# YardMatch scaling review and main consolidation

Reviewed September 20, 2026, against `main` at `4d5b2dd3be3fc2e067f975f65872c4ca3ccadae5`.

YardMatch has concrete bottlenecks that should be addressed before substantial growth. The strongest observed reliability issue is notification delivery under concurrent retries. Provider search and synchronous password verification are the clearest performance risks. Passing the functional suite does not establish production capacity; no production traffic or capacity test was run.

## Findings, ordered for follow-up

1. **High: notification retries can duplicate sends and strand queued deliveries.** [Retry sweep](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:1531), [dispatch](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:23155), and [due selection](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:23211) read records and dispatch without an atomic claim. Two service instances sharing an isolated PostgreSQL database both sent the same due delivery in a controlled probe: two stubbed sends, one delivery row, and a recorded attempt count of one. A separate `queued` row stayed queued after a sweep because only `failed` rows are selected. A crash between creating a queued delivery and dispatching it therefore has no recovery through this retry path. Every external send in the probe was stubbed; no messages were sent to people. Add durable claims with expiring leases, bounded batches/concurrency, recovery of abandoned queued work, and provider idempotency where supported. Exercise overlapping workers and crash recovery in regression tests. Local claims alone cannot guarantee exactly-once external delivery across every crash boundary.

2. **High: searches get more expensive as the entire marketplace grows.** [Provider search](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:1873) loads every provider and booking, filters providers in application code, then queries availability separately for every eligible nearby provider. It scans the booking array again for each candidate. The [repository](/Users/patrickkopps/Documents/app/apps/api/src/repositories/PrismaMarketplaceRepository.ts:569) confirms the booking query has no filter or bound. Work includes roughly `nearby candidates × all bookings` comparisons plus per-provider database queries. This can increase memory, CPU, pool contention, search latency, and eventual timeouts even for a customer in a small local market. Move location/category/readiness/date selection into indexed database queries, fetch candidate availability together, and aggregate relevant booking history. Preserve the current recommendation order and curated alternatives. Similar unbounded repository reads appear in ops, staffing, messaging, and notification paths; audit them by request frequency and query cost.

3. **High: login bursts block unrelated API requests.** [Password hashing and verification](/Users/patrickkopps/Documents/app/apps/api/src/auth.ts:57) use `scryptSync` inside the API process. A local Node v25.9.0 probe warmed up five verifications, then ran 100 serial verifications: 8,387.9 ms total, 83.9 ms each, and a zero-delay timer fired after 8,393.2 ms. Other checks were running on the machine, so these timings are not a production throughput estimate; the timer delay demonstrates blocking. Use asynchronous password derivation with bounded concurrency and retain rate limits and the existing hash format. Node documents the [asynchronous and synchronous scrypt APIs](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options).

4. **High under bursts: external work occupies request and transaction capacity.** [Notification creation](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:23010) immediately awaits vendor dispatch, and the retry sweep launches every due delivery through one unbounded `Promise.all`. Even reading notifications runs retry work. Separately, [calendar synchronization](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:16139) enters a [transaction-scoped lock](/Users/patrickkopps/Documents/app/apps/api/src/repositories/PrismaMarketplaceRepository.ts:96) before [fetching the external calendar](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:16553). Slow feeds can occupy connections and serialize other work for that provider until completion or timeout. Commit notification intent and process it outside customer requests; fetch/parse calendar input before a short locked revalidation/write. Size the total database connection budget across API and worker instances; increasing API replicas alone does not remove these bottlenecks. Prisma provides [connection management guidance](https://docs.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-management).

5. **Medium: the client map eventually loads a provider's complete history.** [Client overview](/Users/patrickkopps/Documents/app/apps/api/src/services/MarketplacePlatformService.ts:4283) uses pages of 200 but drains all pages into memory, queries each customer separately, and loads recurring plans for the whole marketplace. The [client list](/Users/patrickkopps/Documents/app/apps/web/src/components/ProviderClientsBoard.tsx:96) renders all matching properties and the [map](/Users/patrickkopps/Documents/app/apps/web/src/components/ProviderClientMap.tsx:62) creates markers for all coordinate groups. This can become slow for a successful provider with years of visits and many properties, particularly on phones. Build a provider-scoped property summary query, batch customer lookup, filter recurring plans in the database, and introduce list virtualization/map clustering or viewport queries. Preserve access to historical clients when adding bounds.

6. **Medium: analytics has explicit volume ceilings.** [Maintenance](/Users/patrickkopps/Documents/app/apps/api/src/observability/ProductAnalytics.ts:128) exports at most 100 events per [30-second interval](/Users/patrickkopps/Documents/app/apps/api/src/index.ts:43): about 3.3 eligible events/second per healthy non-overlapping loop. Above that rate a single worker accumulates backlog. Multiple instances do not atomically claim distinct batches. [Reports](/Users/patrickkopps/Documents/app/apps/api/src/observability/ProductAnalytics.ts:167) read at most 50,001 rows, report on the first 50,000, and flag truncation; they are not complete reports beyond that cap. Pending persistence also has a 10,000-event bound with drop accounting. Keep these protections, but add worker ownership, measured drain capacity, backlog age alerts, and database aggregates for complete reporting.

The repository includes bounded booking-history queries, request body limits, outbound timeouts, and database-backed security/financial protections. The seven PostgreSQL regressions passed, including cross-instance recovery/checkout and durable financial records. Those safeguards are valuable, but they do not cover the notification race above or prove performance with a large dataset.

## Capacity work still needed

Run a staging benchmark on the intended production topology with realistic historical bookings and properties, geographically distributed providers, login bursts, concurrent searches/bookings, active route updates, and a notification outage/recovery scenario. Measure p95/p99 latency, errors, event-loop delay, memory, database connection wait/lock time, query plans, and queue age. Define acceptable service levels before claiming a supported user count. The checked-in Render blueprint describes staging; live production sizing and vendor quotas were not inspected.

Recommended first engineering batch: repair notification claiming/recovery, remove synchronous password work, and bound the provider-search database workload. Follow with calendar transaction shortening, client-map summaries, analytics throughput, and a mixed-workload load gate.
